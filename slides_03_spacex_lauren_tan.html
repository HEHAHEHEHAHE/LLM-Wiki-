工程師角色的代際轉移

瓶頸從來不是「AI 能不能寫代碼」，而是人類能否以機器速度驗證其正確性，並建構免除重複探索的高信任環境。

舊工程師思維 (手動碼農)

• 以自己親手撰寫每一行演算法為傲。
• 花費大量時間在格式排版、手動測試與逐行 PR 審查。
• 產能受限於人類打字與閱讀生理極限。

新工程師角色 (工廠設計師)

• 退居幕後，擔任軟體工廠流水線的「工具打磨者」。
• 設計可重複調用的 Skills、客製化 Linter 與架構約束。
• 讓同類型的錯誤在發生當下就被環境制度化阻斷。

出處章節：I. 核心訪談背景與演進

核心隱喻：商業後廚與備料台 (Mise en Place)

鈍刀與混亂廚房 (Dull Knives)

• 混亂現場：刀具生鏽遲鈍、砧板污穢、食材隨處堆放。
• 代碼對應：型別缺失、測試龜速、目錄邊界混亂。
• 結果：廚師即使廚藝再高，在出餐壓力下也只能手忙腳亂陷入救火。

頂級備料台 (Mise en Place)

• 標準規範：所有食材精確切片歸位，刀具打磨鋒利。
• 代碼對應：乾淨的架構合約、即時報錯的編譯器、一鍵重現腳本。
• 結果：環境純淨無摩擦，Agent 如米其林主廚般行雲流水穩定交付。

出處章節：II. 核心架構與隱喻拆解 - 1. 商業後廚

治理哲學：給予上下文，而非微觀控制

「Context, Not Control」借鑒自頂級極客文化：對待 AI Agent 亦應如此，絕非依靠微觀控制。

微觀控制的死胡同 (Micro-management)

• 在 Prompt 中塞入上百條瑣碎禁令（「不要動 A，不要寫 B」）。
• Context 嚴重膨脹，模型注意力渙散，反覆違規。

上下文驅動的自主性 (Context-Driven)

• 提供充沛、精確的系統狀態與架構依賴圖。
• 建立硬性環境約束（編譯器與型別系統），讓 Agent 在安全邊界內自主探索最佳解法。

出處章節：II. 核心架構 - 2. Context, Not Control

pstack 理念：Agent Skills 是軟體合約

痛點：Agent 重複探索世界的浪費

• 每個新 Agent 都像失憶者，反覆浪費 10 輪對話摸索專案如何運行。
• 每個 Agent 採取不同做法，導致工程行為無法標準化。

解答：Skills 作為可組合合約 (Contracts)

• Skills 沒有魔法，是自然語言與確定性腳本的標準化封裝。
• 將最佳操作路徑固化為可組合合約，消除認知摩擦。

高階範式：Bug 分診 Skill $\to$ 調用本地重現 Skill $\to$ 調用修復測試 Skill，形成確定性流水線。
出處章節：III. pstack 與 Agent Skills 的本質 ｜ 概念：agent-skills-architecture

實戰閉環：盯緊 Agent 與自主改進閉環

盯緊你的 Agent 如同實習生

• 觀察猶豫軌跡：初期親自觀察 Agent 的每一步思維鏈，找出它在哪裡試圖走捷徑或加註解。
• 環境回饋原則：看到 Agent 寫出壞味道代碼，絕對不責怪模型，而是檢討環境缺少了哪一條 Linter 規則！

卡帕西評分閉環 (Karpathy Loop)

• 客觀評判標準 (Objective Judge)：為任務建立機器可執行的打分機制（測試通過率、效能指標）。
• 自主收斂重構：只要評判標準明確，Agent 就能在無人值守狀態下自我循環重構，直至達標。
